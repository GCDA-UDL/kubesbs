# Fidelity runs, 2026-10-29

KWOK against a real k3s cluster (`modules/real`, PROVIDER=k3d), Alibaba workload
scaled with `utils/scale_base.py` (CPU / 200, memory / 512) and cut at 10, 30, 60
and 100 nodes (82, 287, 670, 1,065 pods). Three runs per platform and size: 36 runs.
The paper's Section "Fidelity Against a Real Cluster", Table `tab:fidelity` and
Figure `fig:fidelity-latency` come from these files (`utils/repro/fidelity_report.py`).

| Folder | Platform | Host | Label in the CSVs |
|---|---|---|---|
| `spoofing-gcd/` | real k3s v1.29.0 (k3d 5.7.4) | 2× Xeon Silver 4210R (20c/40t), 128 GB, Rocky Linux 9.3, cgroups v2 — the reference server of the big sweep | `real`, `k3d-gcd` |
| `spoofing02/` | real k3s v1.29.0 (k3d 5.7.4) | Xeon W-3245 (16c/32t), 192 GB, Ubuntu 20.04, cgroups v1 | `real`, `k3d` |
| `spoofing02/` | KWOK 0.7.0, `KWOK_KUBE_VERSION=v1.29.0` | same | `kwok`, `sim` |

The spoofing02 real runs were made before `REAL_PLATFORM` existed, so their
platform label is plain `k3d`; `fidelity_report.py` takes the platform from its
command line, not from the CSVs.

## Files

- `pods-<tool>-<platform>-<nodes>-<rep>.csv`: per-pod record (`utils/collect_pods.py`):
  node, creation time (watcher, ms), scheduling time (`Scheduled` event, µs), status,
  requests. `*.watch.csv`: the raw watcher log (`utils/watch_pods.py`).
- `real-<nodes>.csv`, `kwok-<nodes>.csv`: the usual KubeRun rows (run time, CPU,
  memory, unscheduled pods). On spoofing02 (cgroups v1) the cost columns are 0.
- `real-<nodes>.log` (spoofing-gcd only): harness logs.
- `load-start.txt`, `load-end.txt`: `uptime` before and after the matrix
  (spoofing02 also lists the GPU utilisation: 0–1 %).
- `DATASET.sha256`: checksums of the dataset (LF line endings), regenerated by
  `bash utils/repro/make_fidelity_dataset.sh`.

## Caveats

- **Latency at 60–100 nodes is an upper bound.** The emulated cluster saturates its
  host: at the end of the 100-node runs, spoofing-gcd had a load average of 206
  (1 min) / 308 (5 min) on 40 threads; spoofing02 a 15-min load of 44 on 32 threads
  at the end of its matrix. The scheduler shares the CPU with every node's kubelet.
- Placement is not affected: the two hosts agree as much as runs on one host.
- Cost of the real cluster (spoofing-gcd): 1.8 GB / ~140 s CPU at 10 nodes, 22.2–22.7 GB
  / 7,100–8,600 s at 100 nodes; memory ≈ 0.16·N + 0.00065·N² GB. A step test on
  spoofing02 (192 GB, 1 run per size) found the CPU, not the memory, to be the limit:
  200 nodes completed (2,094 pods, 21 unscheduled, 459 s, peak load 936), but a second
  200-node attempt on 2026-10-30 was stopped by the load guard at a 1-min load of 1,596
  on 32 threads with 2,048 pods still pending (load at 200 nodes varies from run to run);
  300 nodes hit the 1-hour
  limit with 1,704 pods unscheduled, a load average in the thousands and an unresponsive
  sshd while the cluster was deleted (peak cluster memory ~97 GB, at least 57 GB free);
  at 500 nodes k3d could not start the cluster (Docker timeouts). The study stops at
  100 nodes. Those runs are not part of this folder.
- KWOK is the only simulator compared.

## Regenerate

```bash
bash utils/repro/make_fidelity_dataset.sh
(cd data/fidelity && sha256sum -c ../../results-repro/fidelity-20261029/DATASET.sha256)
F=results-repro/fidelity-20261029
python3 utils/repro/fidelity_report.py --out fidelity-out --nodes-dir data/fidelity/vanilla \
    --real "4210R server=$F/spoofing-gcd/pods-real-*.csv" \
    --real "W-3245 server=$F/spoofing02/pods-real-*.csv" \
    --sim KWOK="$F/spoofing02/pods-kwok-*.csv"
```
